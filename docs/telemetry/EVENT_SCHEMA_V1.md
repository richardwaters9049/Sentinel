# Sentinel Telemetry Event Schema v1

## Purpose

The Phase 1 telemetry contract defines the canonical event format used inside Sentinel after ingestion and normalisation.

The schema is intentionally small enough to remain understandable while still carrying the context required for future detection engineering and threat hunting.

The machine-readable schema lives at:

```text
packages/schemas/telemetry-event-v1.schema.json
```

Current schema version:

```text
1.0.0
```

## Ingestion contract

Telemetry is accepted through:

```http
POST /api/v1/telemetry
Content-Type: application/json
```

The client supplies a source timestamp plus event context. Sentinel adds:

- a generated event identifier when one is not supplied;
- the canonical schema version;
- server-side receive time;
- normalised case/whitespace for selected categorical fields.

Successful ingestion returns HTTP `202 Accepted` after the normalised event has been acknowledged by JetStream.

Persistence is asynchronous.

```json
  "source": {
    "type": "identity",
    "vendor": "sentinel-sim",
    "collector": "simulator-identity-01"
  },
  "asset": {
    "id": "asset-engineering-ws-01",
    "hostname": "engineering-workstation-01",
    "zone": "ot"
  },
  "actor": {
    "id": "user-demo-operator",

  },

```

## Required fields

Every ingested event requires:

- `timestamp`
- `source.type`
- `source.collector`
- `event.category`
- `event.action`

`event_id` is optional at ingestion. Sentinel creates a cryptographically random identifier when it is absent.

## Timestamps

`timestamp` represents the source-observed event time.

`received_at` is generated by the Sentinel gateway.

Both are stored in UTC.

A source timestamp more than five minutes in the future is rejected to prevent obviously incorrect producer clocks from silently polluting event ordering.

Historical events are permitted because future replay/import workflows may need them.

## Event identifiers

Identifiers must:

- be 128 characters or fewer;
- begin with an alphanumeric character;
- contain only alphanumeric characters plus `.`, `_`, `:`, or `-`.

This rule applies to event IDs and entity IDs used by the current normaliser.

## Source

`source` identifies where telemetry originated.

Fields:

- `type` — broad source family such as identity, endpoint, network, OT, or cloud;
- `vendor` — optional producer/vendor label;
- `collector` — concrete collector or simulator identity.

Source type is normalised to lowercase.

## Asset

Asset context is optional because not every event maps cleanly to one host or device.

When supplied, the current contract requires:

- `id`
- `hostname`
- `zone`

Typical zones may include:

- `corporate`
- `dmz`
- `ot`
- `cloud`
- `lab`

The schema intentionally does not hard-code the zone vocabulary yet.

## Actor

Actor context is optional.

When supplied:

- `id`
- `type`
- `name`

are required.

Actor types may later distinguish:

- human users;
- service accounts;
- workloads;
- devices;
- AI agents.

The Phase 1 implementation leaves this vocabulary extensible.

## Event details

`event.category` describes the broad event family.

Examples:

- `authentication`
- `process`
- `network`
- `configuration`
- `file`
- `identity`

`event.action` describes the concrete activity.

Examples:

- `login`
- `process_start`
- `connection`
- `role_assignment`

`event.outcome` is optional.

Common values include:

- `success`
- `failure`
- `denied`
- `unknown`

The system does not yet enforce a closed vocabulary because later telemetry adapters may need additional values.

## Network

Optional network context currently supports:

- source IP;
- destination IP;
- destination port;
- protocol.

IP values are validated using the Go standard library.

Destination port must be between 0 and 65535.

## Labels

Labels provide bounded, low-cardinality scenario or environment metadata.

Limits:

- maximum 50 labels;
- label keys: 1–64 characters;
- label values: maximum 256 characters.

Labels are not a substitute for strongly typed domain fields.

## Normalisation rules

The gateway currently normalises these fields to lowercase:

- source type;
- asset zone;
- actor type;
- event category;
- event action;
- event outcome;
- network protocol.

Leading and trailing whitespace is removed from string fields.

## Validation philosophy

The ingestion boundary follows three rules:

1. reject structurally invalid input;
2. reject clearly impossible or unsafe values;
3. avoid prematurely freezing security-domain vocabularies that will evolve during early development.

The API uses `json.Decoder.DisallowUnknownFields` to prevent misspelled or unexpected top-level/nested fields from being silently accepted.

## Message transport

Normalised events are published to:

```text
Stream:  SENTINEL_TELEMETRY
Subject: sentinel.telemetry.v1
```

JetStream file storage is used locally.

The stream retains events for 24 hours in the current development configuration.

Published messages use the event ID as the NATS message ID, enabling JetStream duplicate suppression within its configured duplicate window.

## Persistence

The durable consumer:

```text
sentinel-event-store-workers-v1
```

reads the telemetry subject and stores accepted events in PostgreSQL.

Persistence is idempotent at the database boundary because `events.id` is the primary key and duplicate inserts use `ON CONFLICT DO NOTHING`.

Asset and identity records are upserted using event timestamps to maintain first-seen and last-seen state.

## Event query API

Stored events can be queried using:

```http
GET /api/v1/events
```

Supported query parameters:

- `limit` — 1 to 200, default 50;
- `before` — RFC3339 source timestamp;
- `category`;
- `asset_id`;
- `identity_id`.

The current response is:

```json
{
  "count": 1,
  "events": []
}
```

A stronger cursor model can be introduced when event volume requires it.

## Versioning

Breaking event-contract changes require a new schema version.

A consumer must not silently interpret an unknown schema version as the current version.

The Phase 1 persistence handler rejects unsupported schema versions.

## Current limitations

Phase 1 does not yet include:

- collector authentication;
- per-producer rate limiting;
- signed telemetry;
- long-term raw event storage strategy;
- schema-registry service;
- dead-letter/quarantine stream;
- full ingestion metrics;
- detection processing.

Those are deliberate later-stage concerns and should not be confused with missing validation in the current vertical slice.
